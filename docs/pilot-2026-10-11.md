### E2E run sheet

Record the exact guest URL and candidate SHA before starting. Open that URL on
two devices and `/host.html` on a desktop. Use headphones. Export the host
metrics once before joining as the test baseline.

| Step | Action | Required result |
| --- | --- | --- |
| 1 | Join from a fresh phone and desktop session | Both guests see and hear each other; host shows two successful joins with join times |
| 2 | Toggle microphone, camera and sound; change camera on phone | The other device confirms every change; remote sound resumes after unmuting |
| 3 | Pin a guest, change view, rotate or fold the phone | Controls remain reachable; video and audio continue |

## Metrics and deployment handoff

The frontend sends cumulative call snapshots in the existing five-second
`/api/events` heartbeat, plus immediate lifecycle updates. The Worker retains the
latest snapshot by revision, so retries/out-of-order requests do not double-count
join events. Older clients still work. Browser/OS/viewport groups contain no raw
user agent, names, device labels, room URLs or credentials.

`/host.html` now displays connected/joining/reconnecting page sessions, attempts,
successful and failed joins, mean/max successful join time, fatal call errors,
device/permission errors, interruptions, and an estimate of connected minutes.
Download metrics before internal testing ends, before the live call, and after
the event. Compare snapshots to separate testing from live totals.

Metrics are browser-reported estimates, not provider billing or proof of media
playback. Reloads create new page sessions; counts are not unique people. Clients
without a heartbeat for 15 seconds are removed from active counts, but their
cumulative metrics remain until evicted from the existing 200-client retention
window. Closed/hidden tabs may lose their last heartbeat. The viewport group is
captured at page load; fold behavior requires manual testing.

Both **Pages frontend and realtime Worker** must run this candidate to expose the
new metrics. Deploy the Worker locally using Wrangler against Didi's existing
Worker name/configuration and credentials; do not target `dugong-preview-realtime`.
No secret rotation or new paid telemetry service is required. Use the existing
deployment procedure and verify telemetry on the actual Pages URL afterwards.

The Worker remains the existing single Didi event backend. The additional event
packages in this repository do not establish event isolation for this pilot.

## Outstanding operational evidence

- Final customer Pages link and deployed candidate SHA.
- Existing Didi Worker identity/version and a successful telemetry round trip.
- Daily room expiry comfortably beyond the expected 9 PM finish.
- Real-device acceptance and prolonged-call results.
- Actual provider participant-minutes/cost reconciliation after the event.

Provisioning warning: `room create --hours ...` reuses any unexpired existing
room; it does **not** extend that room's expiry. Also, creating the default
eight-hour room in the late morning can expire it during tonight's call. Backend
must verify the returned `endDate` and arrange adequate provider room lifetime
before beta testing; requesting a longer duration alone does not fix a reused
room.
